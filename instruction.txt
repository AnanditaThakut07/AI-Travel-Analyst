# Master Prompt — AI Travel Analyst (Full Project Build)

Copy everything below into Antigravity as the initial project prompt.

---

You are building **"AI Travel Analyst"** end to end — a complete data science project that analyzes flight price data, uncovers what drives prices, builds a predictive model, and delivers a working flight recommendation system on top of it. This is a full submission (not a scoped-down version) for a college AI/ML recruitment challenge, and the person who owns this project must be able to explain every design decision in a technical interview. Correctness, clarity, and defensibility of every choice matter more than raw model accuracy.

## What exactly is being built

A complete pipeline with three layers:

1. **Exploration layer** — clean the raw flight dataset, understand its structure, and extract clear, evidence-backed insights about what drives flight prices (route, airline, time-to-departure, stops, duration, season, etc.).
2. **Modeling layer** — engineer features from the cleaned data and train a regression model that predicts flight price from flight attributes, benchmarked against a simple baseline, evaluated with proper regression metrics, and explained via feature importance.
3. **Recommendation layer** — using the trained model and the cleaned dataset, build a **Flight Recommendation System**: given a user's search (source, destination, date, and a stated preference — cheapest / fastest / fewest stops / best overall value), return a ranked shortlist of flights with a clear, inspectable reason for each ranking. This must be a transparent, rule-based scoring system layered on top of the price model — not a black-box collaborative-filtering recommender, since there is no user interaction history in this dataset. This distinction should be stated explicitly in the code comments and the README, since it's a common interview question ("is this really a recommender system?").

All three layers get wired into a single interactive dashboard as the final deliverable, plus at least one stretch goal (SHAP-based explainability) attempted on top.

## Non-negotiable working rules

1. **Work in explicit numbered stages** (listed below). Do not skip ahead, merge stages, or silently reorder them.
2. **After completing each stage**, write a plain-English explanation — assume the reader is new to data science. Cover: what was done, why it was necessary at this point in the pipeline, and what the concrete output/artifact is. Define any non-obvious term in one line the first time it's used.
3. **After each stage's code + explanation is verified working, commit and push to GitHub** with a clean, descriptive commit message (conventional commits style, e.g. `feat: engineer time-to-departure and route-frequency features`). One commit per stage — do not batch stages. Initialize the repo and remote in Stage 0.
4. **Confirm each stage actually runs without errors and produces sensible output** before moving to the next one.
5. Code must be modular (separate files per concern: `data_prep.py`, `features.py`, `model.py`, `recommender.py`, `app.py`, etc.), cleanly structured, and commented only where the logic isn't self-evident — no line-by-line narration comments.

## Stages

### Stage 0 — Project Setup
Initialize git repo + remote, `.gitignore`, `requirements.txt`, folder structure (`data/`, `src/`, `outputs/`, `app/`). Add a placeholder README. Commit: initial scaffold.

### Stage 1 — Data Acquisition & Inspection
Load the dataset, print shape/columns/dtypes/null counts/sample rows. Document the actual schema found (this becomes the "Dataset Used" section basis later). Commit: raw data loading + inspection script.

### Stage 2 — Data Cleaning & Preprocessing
Handle missing values, duplicates, inconsistent formats (dates, time strings, duration strings, currency), and outliers. Justify every drop/impute decision inline. Output a cleaned dataset artifact. Explain: what cleaning means here, what issues existed in this specific dataset, and why each fix was chosen over the alternatives.

### Stage 3 — Exploratory Data Analysis (minimum 5 visualizations)
Produce at least 5 distinct, genuinely informative visualizations — e.g. price distribution, price vs airline, price vs days-to-departure, price vs number of stops, price vs route/source-destination pair, seasonality/day-of-week effects. Choose the plotting library (matplotlib/seaborn/plotly) per chart type rather than defaulting to one. Explain: what each chart shows and the actual insight extracted, not just a description of the chart type.

### Stage 4 — Identifying Major Price Drivers
Use correlation analysis, group-by aggregations, and/or a quick baseline feature-importance pass to rank what actually drives price. Explain: the methodology used to call something a "driver," and the ranked findings in plain language with the evidence behind each.

### Stage 5 — Feature Engineering
Encode categoricals appropriately (be deliberate about one-hot vs target/frequency encoding and justify it), extract derived features (days-to-departure, duration in minutes, departure time-of-day bucket, route as a combined feature, etc.), scale where the chosen model needs it. Explain: what each engineered feature captures and why it should help prediction.

### Stage 6 — Model Building & Evaluation (Part 2)
Train a simple baseline (Linear Regression) and a stronger model (Random Forest or XGBoost — pick one and justify it against the other). Evaluate both with RMSE, MAE, and R² (regression metrics only — no accuracy/precision/recall). Explain: why these models were chosen, how they compare on the metrics, and what the metric values actually mean for someone booking a flight.

### Stage 7 — Explainability (Stretch Goal)
Extract and visualize feature importance from the final model — use SHAP if it runs cleanly in the environment, otherwise fall back to the model's built-in importances and say so explicitly rather than silently downgrading. Explain: which features matter most for predictions and why that lines up (or doesn't) with the Stage 4 findings.

### Stage 8 — Flight Recommendation System (Part 3)
Build the recommendation layer described above:
- Input: source, destination, travel date (or date range), and a preference flag (cheapest / fastest / fewest stops / best overall value).
- Logic: filter the cleaned dataset (or candidate flights) to matching route/date, then score and rank candidates using a transparent weighted formula that combines predicted price, duration, and stops according to the stated preference. "Best overall value" should use a documented weighting, not an arbitrary one.
- Output: a ranked shortlist (top 3-5) with the score breakdown shown, not just a final number, so the ranking is auditable.
Explain: exactly how the scoring formula works, why it's a legitimate content-based/rule-based recommender given the data available, and what its limitations are (e.g. no personalization from user history).

### Stage 9 — Dashboard (Integration Layer)
Build a Streamlit or Gradio app that ties everything together: key EDA visualizations, a price-prediction form, the feature-importance view, and the flight recommender as an interactive search. **This must not look like a default AI-generated app.** Concretely:
- No default framework theme, no centered-logo-and-gradient hero, no generic purple/blue "AI product" gradient, no emoji used as icons.
- Pick one deliberate visual identity: a limited color palette (2-3 colors plus one accent), a real typographic hierarchy (not everything at one default size/weight), and consistent spacing/alignment.
- Treat it like a functional internal analytics tool (data-dense, clear labeling), not a marketing landing page.
- Avoid AI-slop copy ("Welcome to the future of travel! 🚀") — plain, direct labels and section headers.
Explain: what the app does end-to-end from a user's perspective, and how it wires together the model and recommender built in earlier stages.

### Stage 10 — README
Write a complete README: Project Overview, Problem Statement, Installation Instructions, Dataset Used (based on the real schema confirmed in Stage 1), Methodology (all three layers), Technologies Used, Results (metrics + key insights), Challenges Faced, Future Improvements, Screenshots.

### Stage 11 — Final Summary & Interview Explainer
Produce a standalone `SUMMARY.md` (and print it at the end of the run) containing:
1. **Quick recap** — one paragraph covering what the full project does end to end, all three layers.
2. **Architecture walkthrough** — the pipeline stage by stage in 1-2 lines each (Clean → EDA → Drivers → Feature Engg → Model → Explainability → Recommender → Dashboard).
3. **"How to explain this in an interview"** — a script-style walkthrough: what to say when asked "walk me through your project," anticipated questions (why this model over alternatives, why these features, how does the recommender actually rank flights, what would you improve, what was hardest, is this really ML or just rules for Part 3) with short, confident, technically accurate answers to each — written so someone who didn't write the code could read it once and explain the project competently end to end.
